# 快递站老板

手机竖屏普通 HTML/JavaScript H5，目标运行于 TapTap App。原生 ES modules、Canvas 像素场景与 DOM 触控，没有运行时外部依赖。桌面只作预览；横屏保留可滚动竖向站场。

## 玩法与内容

开门流程：选择订单 → 确认并回到站场 → 调配员工 → 玩家点击“开门营业”。确认订单不会投件或启动计时；准备阶段可用“改订单”返回选择，订单与员工分配会保存，重进仍等待开门。

本地1.4.1采用岗位调度：自动收件 → 分拣 → 包装 → 装车 → 发车结算。初始3名工人，各岗1人；玩家拖动具体工人到工位，或点工人再点工位；工位预览来源与目标人数变化，空地放手取消。无需逐件处理包裹。岗位人数改变实际产能，0人会停工并积压；忙碌工人交完手上的包裹再步行调岗。每位工人有持久位置与取货、作业、送货、返回、调岗阶段。

新营业日按批次来货，接单页按顺序显示类型与数量，订单进度下集中显示下一批类型、数量与倒计时。普通件集中到货，异常件拖慢分拣验单、易碎件拖慢包装加固、大件拖慢装车搬运；急件仍自动优先，须在到站后25秒内发车。入口堵住后已到站包裹在料车排队并继续计龄，不因传送带塞满推迟到货。

所有包裹均经过三个岗位。包装台、验单机、加宽入口分别降低加固、验单与大件装车工时，保留特殊货物与普通件的差异；分拣机加快基础分拣。三岗使用真实待处理工作量提示繁忙/停工，相关地面亮起黄/红色，急件临近期限时就地显示剩余时间。分拣格口与扫描仪、包装纸与胶带、装车托盘与坡道各有附着的名称/人数标牌；标牌可点击，工位也可直接接收拖来的员工。

18个营业日横跨梧桐街、河湾、山丘三站，随后可自由营业。第3天引入易碎件、第7天大件、第10天急件、第13天异常件。日渐增加的订单要求招人、买设备、重新分工；钱、设备、人员和历史跨天保留。第2天开放140金员工与170金包装台，第二名员工260金；加密车次220金（第4天）、宽入口350金（第6天）、验单机420金（第12天）、分拣机850金（第14天）。最多5名员工。

稳稳接单与加急专场改变到站节奏、数量和达标奖金；加价线路改变A/B/C订单分布，对应每件多赚2金。接单页并排显示常规/加急的总件数，紧邻显示选中合同所需准时件数与奖金；每条线路按钮直接显示件数，下方显示选中线路额外运费上限。加价线路在接单页确认。车辆自动发车，也可提前点车发货；至少3件集货时每件另加1金。急件须在25秒内发出，迟到失去急件加价与准时信用。运费在真实发车后计入当日收益，日结统一发放；每次营业20金保底，未达标仍可继续。无需广告推进经营。

场景聚焦三个实体工位与员工；车辆收成顶部44px状态行，自动发车倒计时与提前发车仍可操作。视觉坐标投影与点击/拖动共用映射，不改变实际行走工时或存档坐标。

旧版手工分拣逻辑仅用于兼容测试，当前页面会在合法加载后启用流水线模式。

## 存档契约

固定主键 `courier-depot.save.v1`，schema 1；覆盖前写上一代有效原件到 `.backup`。加载完整校验内容、经营阶段、经济与队列；坏档、未知字段/版本和存储异常会停止写入并保留原件，提供导出与重试。保存失败时保留内存进度，重试保存不刷新页面；导出含原件、备份和当前内存进度。

1.1.0在schema1运行态添加可选`shift.processing={id,remaining,duration}`，历史档缺省视为空闲；新档严格校验作业归属和剩余工时。保持固定存储位置、历史收益及已购设备，支持更新后的继续经营，不承诺旧客户端降级读取新运行态。

1.2.0在schema1添加可选`adRewards={pending,grants}`，旧档缺省兼容。广告请求先保存，只有同一请求、同一结算上下文收到明确完整观看回调才发20金；每营业日最多一次，不改写原始营业收益。取消、失败、超时及过期回调不发奖；重进取消未完成请求，不自动播放。奖励保存失败保留内存态，通过原有重试保存入口恢复，已授奖记录防止重复领取。

1.3.0在schema1添加可选`management={version:1,staff:{sort,pack,load}}`与`shift.flow={version:1,pack,load,workers}`。`ENABLE_MANAGEMENT`在原状态对象就地迁移，保留金币、历史、设备、已购员工、广告台账和全部在途货物；旧手工处理保留剩余时间，旧搬运任务延续原剩余作业。每件货仅属于一个队列或员工，调岗目标与当前位置分离，严格校验人数、阶段与货物守恒。新页面首次激活后立即保存，失败使用既有恢复入口，不静默重开。

schema1可选`management.assignments=[{id,targetRole}]`固定每名员工身份与目标岗位，人数须与staff一致，运行中的目标须与flow一致。旧档缺省时从在岗员工或确定性初始名单补齐；调岗、招人和跨天后保存。新员工追加ID，忙碌员工先完成并交付现有包裹再转岗。准备阶段拉开站位方便点选，营业路线和工时保持原值。

schema1可选`plannedOrder={plan,route}`仅允许planning阶段存在。SET_ORDER保存订单草案，START未显式指定的字段从草案读取，成功开工消费草案，NEXT不会把上日订单带到次日。草案未知字段/类型拒绝，历史档缺省兼容。

1.4.0仅新managed营业日增加`shift.flow.rules=2`与`shift.arrivals={version:1,waves:[{kind,count,at}],cursor,waiting}`。清单、到站游标和门外队列持久保存，包裹ID/类型/线路/年龄须与清单一致，未进传送带的包裹同样纳入归属和关门结算。缺少rules的旧营业中存档保持原工时与到货规则，完成后下一天才启用批次；不追改现有作业时钟。后续改变工时或批次生成须保留已支持规则版本，不能用新公式重解释旧运行态。

支持同设备现行 schema1 完整存档加载→继续营业→保存→重进继续保存；冻结样本 `tests/fixtures/schema1-day3.json` 来自2026-10-19实际触摸走完两日后的进度，不能重生成样本掩盖兼容错误。打包必跑相应兼容检查。

支持 Web Locks 的宿主只允许一个页面持有写入权，第二页需关闭前页后重试。无 Web Locks 时仍检查旧原文与 storage 事件，但 localStorage 比较与写入并非原子操作，不承诺任意并发无冲突。无云存档或跨设备同步。清除宿主数据会清除本地进度；备份不会自动替换主档。
