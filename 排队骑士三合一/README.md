# 排队骑士·三合一

手机横屏 H5 卡牌构筑游戏，计划发布到 TapTap。核心循环：杀戮尖塔式三幕路线 + 超级自动宠物式排队交锋 + 炉石酒馆式经营（升本、手牌、三连、发现）。

本文件是项目的**唯一入口**：1.0 的目标与范围、当前实现、开发方式和文档地图都在这里。规则细节以源码为准，文档与源码冲突时改文档。

## 1. 1.0 目标

**1.0 = 现有系统做到“好玩、稳定、能上架”。** 2026-11-15 冻结范围：以当前 94 张流派卡池和支援系统为准，v0.9 规划中尚未实现的批次全部移到 1.0 之后（见 §3）。2026-11-16 架构评审后，局外成长、英雄重做、补给/法术/装备重新分工、敌人出题、金色改为以技能升级为主这五项加入 1.0，系统分工见 [SYSTEMS.md](SYSTEMS.md)。

### 1.2 执行方案（2026-11-16 定）

**工作方式**：每个阶段先写设计（[SYSTEMS.md](SYSTEMS.md) 或对应的设计表），审过再改代码；一批相关改动完成后只跑一次模拟，看两三个关键指标；阶段结束时亲自试玩判断好不好玩；然后提交推送。bot 模拟只用来查异常和看相对变化，不用来判断好不好玩，也不在每个小改动后跑。

**主线**（按依赖顺序）：

| 阶段 | 内容 | 排在这里的原因 | 完成标准 |
| --- | --- | --- | --- |
| 0 | 接替、篝火重复结算修复、架构文档 | | 已完成（2026-11-15/16） |
| 1. 地基 | ① 94 张卡逐张审查：换独立形象、重新命名、设计金色技能升级（每张卡只过一遍）；② 低阶金色削弱身材翻倍；③ 补给 22 / 法术 20 / 装备 29 按新职责归类，列改造、删除、新增清单；④ 接替按流派区分继承比例 | 后续设计都会引用具体的卡和道具，名字和数值先定下来才不返工；同时决定玩家强度基线 | 逐卡表和道具归类表审过；实现后跑一次模拟，看首个金色出现时间和后期换人 |
| 2. 英雄 | 6 名英雄：核心动作 + 每人 5 个分支；开局选择、每幕分支选择界面；立绘 | 依赖阶段 1 的规则基线；英雄是体验差异的核心，越早做越能影响后面的事件和敌人 | 英雄设计审过；实现后第一次真人试玩，看英雄是否真的改变打法 |
| 3. 节点内容 | 按 7 个方向重做事件（SYSTEMS.md §5）、篝火三条路线、拉开地图节点差异、调整商人货物 | 事件奖励使用阶段 1 的道具，也可以出英雄相关事件 | 事件表审过 |
| 4. 敌人与难度 | 每幕主题、精英词条、5 个 Boss 重做（考察流派和站位）；难度阶梯各级规则；整体难度校准 | 难度要对着定型后的玩家强度调；模拟主要在这一阶段使用 | 普通难度没有终局断崖；各级难度梯度清楚 |
| 5. 局外 | 熟练度经验与解锁、每名英雄的难度阶梯、成就、皮肤（广告解锁）；局外存档与一局存档分开 | 解锁内容来自阶段 2 的分支和皮肤、阶段 4 的难度级别 | 从零开始走通第一次通关前后的解锁节奏；第二次真人试玩 |
| 6. 上架 | 接入 TapTap 广告（`src/ui/ads.ts` 目前是模拟）、包体控制（主要是音频）、审核素材（图标、截图、说明、隐私条款）、真机验收 | 内容定型后再做 | 达到 §1.4 |

**支线**（不依赖主线，可随时穿插或单独开会话）：

- **A. 界面与手感**：备战时玩家单位大、敌人缩小，开战转场成对峙；战斗单位放大；招募按钮固定位置；标题画面缩短等待；转场叠层；卡面文字在手机上的字号。
- **B. 美术**：英雄立绘的风格和提示词模板（阶段 2 要用）；新法术和新遗物的专属图标。单位形象在阶段 1 里一并处理（SYSTEMS.md §6）。

其他待办：噩梦的敌人系数 `k = 0.82` 低于困难的 `0.95`，和"敌人再强一截"的描述相反；困难的说明"手气差时不再放水"描述的是已删除的旧机制。两者在阶段 4 一起处理。

### 1.3 平衡现状（数据记录）

以下是 bot 模拟的记录，供阶段 1 和阶段 4 参考。bot 数字只代表相对变化，不等于真人通关率。

- 普通难度通关率：最近一次 bot 模拟（300 局，普通难度，默认老兵队长，能力值 0.65）为 17.3%，终局 Boss 胜率 16%；第一、二幕 Boss 胜率 68%–95%，终局仍是断崖。
- 2026-11-15 修复：bot 在篝火结算后、领完发现奖励再离开节点时会重新打开篝火，每幕能用 4–5 次（`leaveNode` 现在只进一次离开流程）。此前所有 bot 模拟数字都偏高，包括上面原来写的 13.5%；修复后接替改动之前的真实基线是通关 5.7%、终局 Boss 7%。
- 后期商店（2026-11-15 第一轮）：第 13–21 回合 5 个单位里约 4.4 个已是金色，每回合买单位约 0.2 个，金币几乎全花在补给上。已加入「接替」（商店单位拖到不同名队员身上，继承永久加成和装备，见 `run.ts` 的 `takeover`），并按阶层放大高阶身材（`reworkCatalog.ts` 的 `TIER_STAT`），满本时 1–2 阶卡出现率减半（`shopTierWeight`）。改动后通关率 5.7% → 17.3%，后期每回合买单位 0.19 → 0.45、新单位上场 0.09 → 0.21。
- 金色来源（修复后 300 局）：每局约 4.7 个金色，首个金色中位数在第 3 回合；篝火「+2 份」占 42%（每幕一次，几乎必选），商店三连占 40%（平均 1.9 阶），其余是发现、复制法术、点金等。下一步：篝火选项结构、低阶金色收益。
- 待观察：第三幕和终局强度、各流派成型速度、支援品选择效率。

### 1.4 1.0 完成标准

以下数值为建议值，可调整：

- 普通难度 bot 通关率落在约定区间（建议 35%–55%），11 个流派都有通关样本。
- 6 名英雄都有通关样本；局外解锁流程从零开始能走通。
- 至少 3 名真人在手机上完成整局，没有阻断问题，每局时长在 25–40 分钟。
- 844×390、720×360、1280×720 三个视口主流程无遮挡；`pnpm test` 和 `pnpm build` 通过。
- TapTap 广告接入完成，单文件包体积和加载时间达标。

## 4. 开发

```bash
cd source
pnpm install --frozen-lockfile
pnpm dev            # 开发服务，加 ?debug 可在控制台用 window.__app
pnpm test           # 战斗、经营、存档、支援、目标、教程回归
pnpm build          # 字体子集 + 类型检查 + 生产构建（dist/）
pnpm build:single   # 单文件包（dist-single/index.html）
pnpm sim 200 0.65   # bot 整局模拟，用于平衡
```

- `pnpm test` 是唯一的回归入口，新的规则测试加进这里；测试夹具只使用本局开放卡池里的合法单位（`activeCardPool`），否则 v5 存档校验会拒绝。
- 浏览器回归（`pnpm test:ui*`）需要 Playwright 和本机 Chrome，会写入测试存档，请使用独立的浏览器上下文。
- 分析工具（不属于回归）：`scripts/node-stats.ts`（按节点统计 bot 胜负）、`scripts/demos.ts`（检查关键词和单位演示覆盖）、`scripts/import-hourglass-art.py`（从 Duelyst 图集导入单位帧）。
- 样式的加载顺序就是层叠顺序：`main.ts` 先依次加载全局样式（`style.css` → `pixel.css` → `duelyst-units.css` → `global-layers.css` → …），组件样式随各自的 TS 模块导入，`ui/theme.css` 最后加载。`global-layers.css` 和 `prep-features.css` 是按原顺序合并的历史覆盖层，新样式写进组件自己的 CSS 文件，不要再新建按版本或巡检轮次命名的覆盖文件。
- 一次性的调参、审计实验脚本不进仓库。需要保留的结论写进文档，代码依赖 git 历史找回（2026-11-15 清理前的版本为 `6b525de`）。
- `source/output/` 存放本地验证截图和报告，不进仓库。文档中引用的 `output/...` 路径只在当时执行验证的机器上存在。
- 新增中文文案后需要重新跑 `pnpm build`，字体子集会随之更新。
